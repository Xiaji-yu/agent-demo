## H1 沙箱 `zip` 可执行任意命令

- **问题**：`permitted()` 的 zip 分支 `return True, ""` 零校验。Info-ZIP 的 `-T` 会执行测试命令，`-TT cmd` / `--unzip-command=cmd` 可替换 unzip（内部 `system()`）→ 任意命令执行，架空「无 shell + 路径遏制 + 白名单」。
- **修法**（`agentcore/workspace/runner.py`）：zip 收敛为白名单开关 `{ -r, -q, -9, -j }`；任何以 `-` 开头且不在白名单内的参数一律拒绝；**任何含 `=` 的参数一律拒绝**（直接封死 `--unzip-command=...` 形态）。
- **回归用例**：`tests/test_review_h_fixes.py::TestZipWhitelist`（4 类攻击形态 + 破坏性开关 `-m/-d/-@/-P/-e/-x/--out` + 正常打包放行）。
- **复验**：原 PoC `zip o.zip a.txt -T --unzip-command=touch <marker>` 现在被拒（不再落标记）。

## H2 沙箱 `curl` 无 scheme 参数绕过内网判定（SSRF）

- **问题**：只收集含 `://` 的参数做 https + IP 校验；裸 `host:port/path` 被跳过，而 curl 视其为 `http://` → 「https 诱饵 + 裸内网地址」即可 SSRF，实测读到 loopback 内容。
- **修法**：**所有非选项参数一律视为 URL 候选**，逐个要求 `https://` 且 `ip_literal_is_safe(host) is not False`；选项白名单同时收紧（修掉 `--proxy=...` 因含 `://` 被跳过的漏洞）。
- **回归用例**：`TestCurlUrlValidation`（裸内网/169.254 元数据/plain http/`-T`/`--upload-file`/`-x`/`--proxy=`/`-k`/`-K` 全拒；正常 https GET 放行）。
- **复验**：原 PoC（本地 http.server + 裸 `127.0.0.1:PORT/secret.txt`）现在判定拒绝，不再泄漏。

## H3 `calc` 的 `pow()` 算力炸弹

- **问题**：`_reject_pow_bomb` 只查 `ast.BinOp(Pow)`，`pow(...)` 是 `ast.Call` 完全绕过；`asyncio.wait_for(to_thread(...))` 无法取消线程 → 实测阻塞事件循环 **7.19s**、峰值 RSS **473MB**，且 `calc` 是 public 权限（任何用户可打，阻塞期全机器人卡住）。
- **修法**（`agentcore/skills/basic_tools.py`）：把 `pow()` 调用与 `**` 同等对待——计入幂运算次数、指数必须是 ≤1000 的字面常量、禁止指数内嵌套幂。
- **回归用例**：`TestPowBomb`（`pow(2,999999999)`/`pow(2,n)`/`pow(2,99999)` 静态拒绝；`evaluate` 在 **<1s** 内返回错误；`pow(2,10)` 正常）。
- **复验**：修复前 7.19s/473MB → 现在静态拒绝、耗时毫秒级。

## H4 NapCat 超时被误判为「确定未送达」→ 重复投递

- **问题**：`is_uncertain_send_error` 只认 `TimeoutError` 与异常文本含 "timeout"；`httpx.ReadTimeout` 既非 `TimeoutError` 子类、`str()` 又为空 → 返回 False → 超时被当作"没发出去" → 降级重发，用户收到两遍。
- **修法**（`agentcore/skills/file_sender.py`）：增加 `isinstance(err, httpx.TimeoutException)` 判定（出站分层 `outbound._is_uncertain_failure` 复用该函数，一并受益）。
- **回归用例**：`TestUncertainSendError`（Read/Connect/Write/Pool Timeout 均判为 uncertain；`TimeoutError`/`asyncio.TimeoutError` 保持 True；`ValueError` 仍为 False）。

## H5 停机钩子逆序 → flush 在连接池关闭后执行（消息丢失）

- **问题**：NoneBot 停机钩子 `reversed()` 执行；插件钩子后注册故先跑并 `memory.aclose()`，bot.py 的 `flush_all()` 后跑 → 首次 DB 调用 `AttributeError` → 被兜底吞成 `[echo] 用户原话`，消息与回复都不落库/归档（每次重启必现）。
- **修法**：新增 `plugins/qq_agent_adapter/lifecycle.py::shutdown_agent()`，把顺序固定为「停调度 → **flush 防抖** → 关 memory 池 → 关闭共享连接」，每步独立容错且幂等；**bot.py 与插件钩子都调用它** → 正确性不再依赖注册顺序（`nb run` 无 bot.py 的入口也自动覆盖）。
- **回归用例**：`TestShutdownOrder`（顺序断言 `sched:stop → deb:flush → mem:aclose`；单步失败不阻断后续；二次调用幂等；全 None 不抛错）。
- **复验**：真实 `Lifespan` 实验确认执行序为 `plugin:aclose -> bot.py:flush`（即修复前顺序确实是坏的），修复后两个钩子各自内部均为 flush→aclose。

## 1. 备份：`_backup_jsonl` 改游标流式

| 问题 | 改法 | 回归 |
|---|---|---|
| 每张表 `await conn.fetch("SELECT * FROM t")` 整表进内存（大表下同时是内存峰值与事件循环停摆来源） | 抽出 `_iter_table_jsonl(conn, table, batch_rows=500)`：`async with conn.transaction()` + `async for record in conn.cursor(...)`，每满 `_JSONL_BATCH_ROWS` 行交给 `asyncio.to_thread(_serialize_rows, ...)` 序列化并 yield `(chunk, n)`；尾批单独 yield（恰好整除时不多产出空批）；`_backup_jsonl` 消费该生成器，失败时仍删 `.part` | `tests/test_backup_jsonl.py`（7 条：分批/空表/整除/元信息+校验和+0600/首行前失败/迭代中途失败**清理 `.part`**/真库 1200 行） |

**变异复核**：把 `_iter_table_jsonl` 退回 `conn.fetch` 整表 + 单次序列化 → 单测 6 条 **全红**、真库用例也红（`max(seen_batches)=1200 > 500`）。

| 漂移 | 原状 | 改法 |
