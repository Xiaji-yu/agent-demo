### 1.2 推翻：第一轮 §4-6「loguru 桥接无问题」在生产启动顺序下不成立 → 本复核 **XM-1（M）**

- **位置**：`bot.py:31`（`bridge_loguru(_file_handler)`）早于 `bot.py:49`（`from nonebot import ...`）；
  `nonebot/log.py` 模块级 `logger.remove()`（无参=移除全部 sink）；`agentcore/logging_setup.py:89` 的 `logger.add(_sink, ...)`。
- **机制**：sink 先加，nonebot import 时 `remove()` 把它清掉——`loguru sinks after bot import: [2] / sink count: 1`。
- **证据**【已复现，主代理】`timeout 180 .venv/bin/python /tmp/opencode/repro_f_real_bot.py`（**真 bot.py 完整 import**，`AGENT_LOG_DIR` 指向 /tmp）：
  ```
  => 框架日志进入 agent.log： False     # FRAMEWORK MARKER 只进 stdout
  => 对照组（stdlib 日志）进入 agent.log： True   # 同一 file handler 工作正常，死的只是桥接
  ```
  对照 `repro_e2.py` 量化：bridge 后 sinks `[0,1]` → nonebot import 后 `[2]`（id=1 被 remove）。
- **影响**：ccc4b90 与 CHANGELOG 1.0.5「框架日志进 `data/logs/agent.log`——排障不再必须同时翻 journald」
  **在所有部署形态下不成立**（入口统一 `python bot.py`）。NoneBot 吞 handler 异常后的
  `Running Matcher failed. AttributeError...` 这类 ERROR 仍只进 journald——即 1.0.5「私聊全静默」事故的
  复发面原样保留：事故根因类异常的日志可见性承诺落空。`TestLoguruBridge` 两条全绿是因为测试进程里
  nonebot 已被 conftest 先 import（`remove()` 早已执行完），**覆盖不到生产顺序**（全仓无任何测试 import `bot.py`）。
- **第一轮为何漏掉**：其线3 只验证了「桥接函数本身工作」（在 nonebot 已 import 的进程里调 bridge），
  未验证 bot.py 的**调用时序**。教训与 §5「单文件变异假阴性」同型：模块级 import 副作用只有在
  特定 import 顺序下显形。
- **建议**：`bridge_loguru` 移到 nonebot import / `init()` 之后（`load_plugins` 之前）；补一条
  「未 import nonebot 的进程先 bridge 再 import nonebot，断言 sink 仍在」的回归（子进程跑）。

#### XM-4（M，已复现）`/update` 与 `/update` 并发：第二次的「拒绝」账目覆写第一次，回执误导且可永久丢失
`update_cmd.py:173-182`（唯一并发守卫判 `_running_reason()`，而脚本只在终态/rolling_back/restarting
才写 state）→ A 在 fetch(180s)→merge(120s)→uv sync(900s)→冒烟(180s) 最长 ~1200s 的链里，
`update.json` 躺着**上一次终态** → B 被放行 → B 的 `acquire_lock()` 失败 → 当前 status 是旧终态，
B 用 `refused` **覆写** → A 的 watcher 把它当 A 的结果，给 **A 的目标**发「未更新：已有更新在运行」
并 return；A 随后写的真终态已无人投递（`up_to_date` 不重启 → 无新进程接手）。
【已复现】`.venv/bin/python -m pytest /tmp/opencode/repro_update_race.py -q -s`：
`A 的 watcher 实际发出： ['private:10000 <- 未更新：已有更新在运行']`，终态 `up_to_date` 的
`notified` 未置、无人投递。第一轮 M4 只覆盖 `/reboot` 的两个入口，`/update` 入口自身在盲区。
建议 `_running_reason()` 改判 `update.lock` flock（与 `update_in_progress()` 同判据）。

#### XM-5（M，已复现）回滚备份的 `runtime.patch` 在回滚后**无法** `git apply`（三处声称不成立）
`scripts/self_update.py:340-346`：`_backup_runtime_changes` 在 merge **之后** reset **之前**跑，
`git diff` 的 a 侧是 **target 提交**内容；patch 唯一用武之地是 reset 到 `prev` 之后——两侧基线不一致。
【已复现】scratch 仓实测：`git apply runtime.patch` → `error: data/x.txt：补丁未应用`；
`--check` 同错。docstring「可 git apply 的 patch」+ `docs/operations.md:294-299` + CHANGELOG 1.0.7
三处声称均不成立；真正能救回数据的只有 `files/` 原文副本。另只备 worktree-vs-index，staged 改动
能过 preflight、会被 `reset --hard` 丢、却不进备份（L，同函数 :344-355 vs :213-215）。
建议 patch 旁落 `BASE` 记录 target sha，或文档改为「文件原文副本为准」。
